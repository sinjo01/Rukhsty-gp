Rukhsty | رخصتي — System Requirements

Digital Driving License Management Platform — Jordan

Functional Requirements (FR)

ID Requirement Description Actor Priority
FR-01 User Registration Citizens must be able to register a new account by providing their email and password. The system verifies the email is unique before creating the account. Citizen High
FR-02 User Login / Logout All users (citizen, officer, admin) must be able to log in using email and password. The system issues a JWT token valid for 7 days. Users can log out at any time, clearing the session token. All Roles High
FR-03 Role-Based Access Control The system enforces role separation: USER, TRAINING_CENTER_OFFICER, MEDICAL_CENTER_OFFICER, THEORY_EXAM_OFFICER, PRACTICAL_EXAM_OFFICER, and ADMIN. Each role can only access its designated pages and API endpoints. All Roles High
FR-04 Complete Citizen Profile Citizens must fill in their personal details (first, second, third, family name), national ID, phone, governorate, city, address, and upload a personal photo, ID front and back images before submitting a license application. Citizen High
FR-05 View Profile Summary Citizens can view their stored profile information and profile completion percentage from their dashboard. Citizen Medium
FR-06 Apply for Driving License Citizens can initiate a new driving license application by selecting a license service. The application moves through a defined status pipeline: DRAFT → PROFILE_SUBMITTED → TRAINING_CENTER_SELECTED → TRAINING_COMPLETED → LICENSE_ISSUED / REJECTED. Citizen High
FR-07 Select Training Center Citizens can browse available training centers and select one for their application. The system records the selected center and transitions the application status accordingly. Citizen High
FR-08 Upload Documents Citizens can upload required documents (personal photo, national ID front and back) during the profile completion step. The system stores document URLs and validates that required fields are present. Citizen High
FR-09 Track Application Status Citizens can view all their applications, their current status, and step-by-step progress through the licensing pipeline. Each application detail page shows full history and associated appointments. Citizen High
FR-10 Book Appointment Citizens can book appointments for each stage of the licensing process (training, medical, theory exam, practical exam). The system records the date, center, and type of appointment. Citizen High
FR-11 View Upcoming Appointments Citizens can view a list of all upcoming booked appointments with date, time, center name, and appointment type from their appointments page and dashboard summary. Citizen Medium
FR-12 Receive Notifications The system automatically creates in-app notifications for key events (application status changes, appointment confirmations, exam results). Notifications show a title, message, and timestamp. Citizen Medium
FR-13 Mark Notifications as Read Citizens can mark individual notifications as read or mark all notifications as read at once. The dashboard shows the count of unread notifications as a badge. Citizen Low
FR-14 View Digital License Card Once a driving license is issued, citizens can view a digital representation of their license card including license number, category, issue and expiry dates, and personal information. Citizen High
FR-15 Officer Dashboard Officers see a dashboard summarising their assigned appointments count, today's schedule, and recent activity relevant to their role. Officer Medium
FR-16 View Assigned Appointments Officers can view all appointments assigned to their center, filtered by status (BOOKED, COMPLETED, CANCELLED). Each entry shows the citizen name, appointment type, and date/time. Officer High
FR-17 Record Training Completion Training center officers can mark a training appointment as completed, triggering an application status update to TRAINING_COMPLETED and creating a notification for the citizen. Officer High
FR-18 Record Exam / Medical Results Medical, theory exam, and practical exam officers can record pass/fail results for each stage. A pass progresses the application; a fail can trigger rejection or re-scheduling. Officer High
FR-19 Admin Dashboard & Statistics Admins see a high-level statistics page: total applications, pending reviews, issued licenses, active users, and recent system activity. Admin Medium
FR-20 Manage All Applications Admins can view all citizen applications across the system, filter by status, and drill down into individual application details. Admin High
FR-21 Approve / Reject Applications Admins can approve an application (advancing it toward license issuance) or reject it with a written reason. The decision is saved, the application status is updated, and the citizen receives a notification. Admin High
FR-22 Issue Driving License Admins can issue a digital driving license for an approved application. The system creates a license record with a unique number, license category, issue date, and 5-year expiry date. Admin High
FR-23 Manage Users Admins can view a list of all registered users, see their roles, registration date, and account status (active/inactive). Admin Medium
FR-24 Manage Training Centers Admins can view all registered training and examination centers, including their location (governorate, city), capacity, type, and assigned officers. Admin Medium
FR-25 Bilingual Interface (AR / EN) The platform displays all UI text in both Arabic and English where applicable (headings, labels, placeholders). Arabic content is RTL-aware. All Roles Medium

Non-Functional Requirements (NFR)

ID Category Requirement Description Priority
NFR-01 Performance API Response Time All API endpoints must respond within 500 ms under normal load. Database queries must use indexed columns to avoid full-table scans on frequently accessed tables (users, applications, appointments). High
NFR-02 Performance Page Load Time The frontend SPA must achieve an initial load time under 3 seconds on a standard broadband connection. Code-splitting and lazy-loading are applied per route to minimise bundle size. Medium
NFR-03 Security Authentication & JWT All protected endpoints require a valid JWT Bearer token signed with a secret key. Tokens expire after 7 days. Invalid or expired tokens return HTTP 401. Passwords are hashed using bcrypt (cost factor 10) and are never stored in plain text. High
NFR-04 Security Authorization & Role Guards Every API route enforces role-based middleware. Accessing a route outside a user's assigned role returns HTTP 403. The frontend additionally restricts navigation using per-route role checks in the AppShell component. High
NFR-05 Security Input Validation All API request bodies are validated server-side using Zod schemas before processing. Invalid payloads return HTTP 400 with descriptive error messages. SQL injection is prevented by parameterised queries via Drizzle ORM. High
NFR-06 Security HTTPS & Secure Transport In production, all client-server communication is encrypted over HTTPS/TLS. The reverse proxy enforces mTLS for internal service-to-service routing. Sensitive credentials are stored as environment secrets, never hard-coded. High
NFR-07 Usability Responsive Design The platform is fully usable on desktop (1280 px+), tablet (768 px), and mobile (375 px) screen sizes. Tailwind CSS utility classes provide a fluid, adaptive layout across all breakpoints. High
NFR-08 Usability Dark / Light Mode The interface supports both light and dark colour modes, toggled by the user. The selected preference is persisted via the ThemeProvider and applied globally across all pages. Medium
NFR-09 Usability Animated Transitions Key page transitions and component state changes use Framer Motion animations (fade-in, slide-up) to provide smooth, professional UX without blocking user interaction. Low
NFR-10 Usability Error Feedback The system provides clear, actionable error messages via toast notifications for every failed operation (login failure, form validation errors, API errors). Generic "something went wrong" messages are avoided. Medium
NFR-11 Availability System Uptime The deployed platform targets 99.5% monthly uptime. The Express API server is managed by a process supervisor and restarts automatically on crash. PostgreSQL data is persisted on a reliable managed database service. High
NFR-12 Availability Graceful Error Handling Unhandled API errors return a structured JSON response (message, status code) instead of crashing the server. The frontend displays user-friendly fallback states (empty states, retry buttons) when data fails to load. High
NFR-13 Maintainability Contract-First API The API contract is defined in an OpenAPI 3.0 specification. Client hooks and Zod schemas are auto-generated via Orval codegen. Any API change requires updating the spec first, ensuring frontend and backend stay in sync. High
NFR-14 Maintainability TypeScript Strict Mode The entire codebase (frontend, backend, shared libraries) is written in TypeScript with strict mode enabled. Zero TypeScript errors are permitted in CI. This reduces runtime bugs and improves refactoring safety. High
NFR-15 Maintainability Monorepo Structure The project uses a pnpm workspace monorepo separating concerns: api-server, rukhsty web app, db schema lib, api-spec lib, and api-client-react lib. Shared code lives in libs to avoid duplication. Medium
NFR-16 Maintainability Structured Logging The API server uses Pino for structured JSON logging. All requests are logged with method, URL, status code, and response time. Console.log is prohibited in server code. Medium
NFR-17 Scalability Stateless API Design The API server is stateless — all session state is encoded in the JWT token. This allows horizontal scaling by running multiple API server instances behind a load balancer without sticky sessions. Medium
NFR-18 Scalability Database Indexing Foreign key columns and frequently queried fields (userId, applicationId, status, email) are indexed in the PostgreSQL schema to maintain sub-100 ms query times as data volume grows. Medium
NFR-19 Compliance Data Privacy Personal data (national ID, phone, photos) is accessible only to the authenticated citizen who owns it and authorized admin users. Officers can only see citizen data relevant to their assigned appointments. High
NFR-20 Compliance Audit Trail All significant state changes (application status updates, license issuance, admin decisions) are recorded in the audit_logs table with the actor's user ID, action type, entity affected, and timestamp. Medium
